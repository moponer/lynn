## 0. 结论速览

用户设想 = 把「会话」升级成「工作群」：一个群 = 一条任务线 = 一支团队 = 一个 Pi 会话；群里左边是成员（AI 执行单元）与风铃，右边是你；@某人 = 定向诉求；群内消息 = 当前任务的追加，新任务必须另开群。

**可行性：高。** 视觉改动很小（三栏骨架、左栏会话列表、右栏编制表都已存在且已有分组折叠），**语义与数据改动是主体**：

| 维度 | 现状 | 目标 | 改造量 |
|---|---|---|---|
| 群容器 | `thread`（会话） | 同一实体，加「群」语义 | 小（加字段） |
| 消息作者 | `FeedCard.kind` 四值，成员无发言位 | `FeedCard.author`（user/lynn/member/system） | 中（契约+渲染+产出点） |
| @ 提及 | 只支持文件，且被剪掉转附件 | @成员为实体，留在正文 | 中（Composer+内核解析） |
| 风铃动作 @ | 无 | 派单/催促/打回/验收自动 @成员 | 中（工具层强制） |
| 群内消息语义 | 风铃自行判断新任务/合并/追加 | 群内=追加；新任务另开群 | 中（提示词+闸） |
| 右栏 | 按 teamId 分组折叠 | 本群置顶展开，他群折叠 | 小（已有折叠，改排序） |
| 成员右键 | 无 | 资料/目标/进度/@TA/催一下 | 中（新 RPC+菜单） |

## 1. 概念映射：飞书群 → 风铃群

飞书群的三个要素，逐一映射：

| 飞书要素 | 风铃里的对应 | 说明 |
|---|---|---|
| 群容器（群名/成员/公告/置顶） | `thread`（会话）+ `team`（团队） | 一群 = 一条任务线 = 一支班底；**一线程一队已是事实**（`resolveTeamId` 的启发式：`kernel.ts:4429-4441`） |
| 群主 | 用户（你） | 群里唯一有决定权的人 |
| 群成员 | 风铃 + 招聘进来的成员 | 成员是 AI 执行单元，不是真人 |
| 机器人成员 | 风铃（群里唯一的机器人，且是唯一执行者） | 成员**没有执行工具**，风铃才有调度权（`persona.ts:19`） |
| 消息流 | `FeedCard[]` | 唯一的时间线 |
| @某人 | 定向诉求 → 风铃转译成工具动作 | **不是**直接把消息丢给成员 |
| 置顶 / 未读 | `ThreadMeta` 需新增 `pinned` / `lastReadAt` | 现无 |

**与微信/飞书的关键差异（决定了不能照抄）：**

1. 成员是 AI，不是人 → 成员**不主动发言**，只在「交回报 / 卡住 / 求助」时进群发言。否则一屏刷满进度条。
2. 用户**不能直接指挥成员** → `@成员` 的语义是「向风铃提出针对某人的诉求」，风铃再落到 `nudge_member` / 返工 / 新派单。
3. 群里所有动作都要留痕 → 风铃的每次调度在群里是**一条 @成员 的消息**，这正好是"工作群"的正确形态（微信工作群里 AI 领队的调度记录）。

## 3. 消息语义与 @ 规则（核心）

### 3.1 语义表

| 群里发生什么 | 谁看得到 | 风铃该做什么 | 落地工具 |
|---|---|---|---|
| 你发消息，**不 @** | 仅风铃 | 自己处理（回答/决策/派单/汇报） | 常规回合 |
| 你发消息，**@成员X** | 风铃 + X 的相关上下文 | 把诉求转达给 X；在跑的用补话，已交的用返工，没单的用新派单 | `nudge_member` / `assign_task(reworkTaskId)` / `assign_task` |
| 你发消息，**@风铃** | 风铃 | 同"不@" | 常规回合 |
| 风铃派单 | 全群 | 卡上 @承接成员 | 工具层自动 |
| 风铃催促/打回 | 全群 | 卡上 @该成员 | 工具层自动 |
| 风铃验收 | 全群 | 卡上 @该成员 | 工具层自动 |
| 成员交回报 | 全群 | 成员发言（带头像），并 @风铃 | 成员回报通道 |
| 成员卡住/求助 | 全群 | 成员发言 @风铃 | 成员回报通道 |

### 3.2 风铃侧硬规则（写进提示词 + 工具层双保险）

1. **群里发起的动作必须 @到人**：派单、催促、打回、验收、停单，正文都带 `@成员名`。
2. **@成员 = 定向**：风铃不得把 @X 的诉求当成全队广播，也不得忽略。
3. **@未回应要兜底**：群里有 @ 但风铃没回应 → 心跳巡检事实新增一类「群内 @ 未回应」（接 `heartbeat.ts` 现有三类事实）。

### 3.3 群内消息 = 当前任务的追加

用户诉求核心：取消"任意消息进任务池、由风铃自行分类"。

改造后：

- 群内输入框固定语义：**本群追加**（补充要求 / 回答风铃的提问 / 催进度 / 追问口径）。输入框占位文案随群状态走：`在本群追加…（新任务请开新群）`。
- **新任务 = 点左栏 `+ 新群`**。新群初始只有「你 + 风铃」，风铃在本群内招募成员、派单、验收、汇报——用户设想的「群内由风铃进行招募/派单/验收汇报」原样成立。
- 群内消息若**明显是别的事**（风铃判定为新任务）：风铃**不擅自开工**，回一句「这是新任务，另开一群（点左栏 +）」；且 `assign_task` 在 P1 加一道「群任务纯净性」闸——派单若与本群目标无关，工具层拒绝并要求开新群。

风铃现在的判定依据（`persona.ts:12` 接单三问、`persona.ts:15` "开新任务新建团队不复用旧班底"）只覆盖"要不要组队"，不覆盖"是不是另一件事"，需补规则。

### 3.4 一条消息的完整生命周期（目标链路）

```
你: @阿明 这段口径按季度重出            → feed.send(text, mentions=[阿明])
  内核: 解析 @ → 校验是本群成员 → 落 user 卡（author=user, mentions=[阿明]）
        history.push(user content 含 "@阿明 …")
风铃: 收到 → 判定「@X 且 X 在跑」 → nudge_member(taskId, "用户原话：这段口径按季度重出")
  内核: nudge_member 落地 → 群里发一条 lynn 卡，正文 @阿明  ← 工具层强制
成员: 下一轮收到补话 → 改完交回报 → 成员卡（author=member）正文 @风铃
风铃: 读产物（read_artifact）→ 验收 → lynn 卡 @阿明 + 汇报卡
```

注意：**成员侧上下文仍由风铃转译**（成员看不到群对话，`persona.ts:13`），这与飞书不同但更安全，保留。

## 4. 数据模型变更

### 4.1 `FeedCard`（`src/shared/contract.ts:346-385`）

```ts
export type AuthorKind = "user" | "lynn" | "member" | "system";

export interface FeedAuthor {
  kind: AuthorKind;
  name?: string;        // 成员名 / "风铃"
  memberId?: string;    // 成员唯一键 = name（team-store.ts:26-50）
  teamId?: string;
  role?: string;
  avatarId?: string;
}

export interface FeedCard {
  // …现有字段
  author?: FeedAuthor;   // 新增：无则回退到 kind 的旧语义（向后兼容）
  mentions?: { kind: "member" | "lynn"; name: string; memberId?: string }[];  // 新增
}
```

`kind` 保留不变（`user`/`lynn`/`tool`/`system`），`author` 为叠加维度：`kind:"tool"` 且 `author.kind:"member"` = 成员的动作卡（派单/回报）；`kind:"member"`… 不新增 kind 值，避免破坏 552 条既有测试与快照。

### 4.2 成员发言如何成为一等消息

成员现在只有 tool 卡（`appendProgress` `kernel.ts:1147-1186`；回报 `kernel.ts:2103-2109`、`:2521-2527`），靠 `title: "成员名 · taskId"` 标识作者。改造：

- 成员回报 → `kind:"tool", badge:"回报", author:{kind:"member", name, memberId, teamId, role, avatarId}`，正文提到最前（不再埋在 title 里）。
- 成员进度 → 保持 tool 卡（折叠），但补 author（点击展开能看到是谁在做什么）。
- 成员**对话体**（卡住时求助、交付时的结论）→ `kind:"lynn"`? 不行。新增 `kind:"member"` 会碰多处 switch。

  → **推荐**：`author.kind === "member"` 时，渲染层走"成员消息"样式（带头像+名字+角色），无论底层 kind 是 `tool` 还是新增 `member`。这样**契约层零破坏**，视觉层完全达到群聊效果。成员消息默认**不折叠**（区别于工具卡 `<details>`）。

### 4.3 群与团队的显式绑定

现状：`TeamRecord`（`team-store.ts:208-220`）**没有 threadId**，团队归属靠启发式（`kernel.ts:4429-4441`）。群化后必须显式：

- `TeamRecord` 增 `threadId?: string`；建队时写入。
- `resolveTeamId` 改为：本群 teamId 优先 → 其次"唯一在职队且从未做过任务" → 否则新建队（保持"新任务新建班底"）。
- 本群成员 = 本群所有工单的承办成员 ∪ 本群 team 的成员（派生，不落盘）。

### 4.4 `ThreadMeta` 增字段

```ts
pinned?: boolean;
lastReadAt?: string;
// group?: { teamId?: string; kind: "task" | "chat"; memberIds?: string[] }  // 可选，派生优先
```

### 4.5 `@` 的解析与落地

- Composer：`detectMention`（`Desk.tsx:2479-2497`）现只搜文件且命中即剪掉。改为**双通道**：
  - `@文件` 保持现状（剪掉 + 进随附条）；
  - `@成员` **保留在正文**，插入一个不可见的结构化标记（推荐 `{{m:阿明}}` 前端渲染成蓝色 @ 芯片），发送时解析成 `mentions[]`。
- 内核二次校验：以**本群成员名单**为准，陌生 @ 名字丢弃并回一句"群里没有这个人"（防模型幻觉成员名）。
- `feed.send` 增 `mentions` 参数（`kernel.ts:5361-5402`）；`history.push` 的 user content **保留 `@名字` 文本**（模型要看见），结构化 targets 供内核判定。

### 4.6 前缀缓存注意

记忆里已有前缀缓存优化（技能注入移出 systemPrompt 等）。@mention 解析必须：
- **不改 systemPrompt**（群规则走 persona/工具描述的既有通道）；
- mentions 拼在**当轮 user 消息尾部**（同 `pendingSkillText` 做法），否则每条 @ 都作废历史前缀缓存。

## 8. 待拍板的 5 个点

1. **成员发言密度**：只在回报/结论/求助时进群（推荐） vs 每步进度都进群（会刷屏，像值班日志）。
2. **用户消息右对齐的视觉**：保值台直角块 + 色条只做左右归属（推荐，保规范） vs 真·微信气泡（圆角+绿白底，与整站"账目感"冲突）。
3. **群内新任务**：风铃拦下提示另开群（推荐，语义最干净） vs 风铃自动另开新群并把原消息搬过去（省一步，但群数会涨）。
4. **@成员的执行路径**：风铃转译（`nudge_member`/返工/新派单，推荐，成员仍只听风铃） vs 允许用户直接给成员留言（成员上下文要引入用户身份，破坏"成员只看简报包"的红线）。
5. ~~**群里用户@成员后，风铃是否必须当轮回应**~~ → **已定（2026-11-12）：走心跳兜底，不强制当轮回应。** 群里 @ 未回应由心跳巡检捞出来，风铃在下一轮补上；代价是延迟（默认心跳 5 分钟），换来不翻车、不烧额外 token。落地见第 6 节 P1-6 与第 11.4 节。

## 11. 借鉴参考：Khazix `leader` skill（2026-11-12 评估）


来源：`https://github.com/KKKKhazix/khazix-skills`（MIT，22.2k star）里的 `leader/SKILL.md` —— "帮你把一句模糊的想法定义成一个清晰的目标"，产出是一份可粘进 `/goal` 的目标任务书。

### 11.1 结论：方法论可吸收，**不建议直接装进 lynn**

| 差异 | leader skill | 风铃（lynn） |
|---|---|---|
| 角色 | 领导（用户）→ 管理者（agent）→ 执行者（另一个 agent） | 用户 → 风铃（管理者，**无执行工具**）→ 成员（执行者） |
| 产出 | 一份 Markdown 任务书，给人粘贴 | 工单 + 契约卡 + 群消息 + 产物 |
| 前提 | agent 自己能跑验收命令（"每条命令你必须亲手跑过"） | 风铃**没有执行工具**（`persona.ts:19`），无法亲手跑命令 |
| 场景 | 长程自主跑几小时 | 群内闭环 + 验收 |

直接装会出事：leader 的触发语（"帮我给 agent 写个目标"）会让 `matchSkills` 命中并把正文注入风铃当轮上下文（`pendingSkillText`），风铃会突然切换成"写任务书模式"，产出 Markdown 而不是工单 —— 与 lynn 的工单/契约卡/证据链机制正面打架。**吸收方法论，不装包**。

### 11.2 目标七问 → 风铃派单简报（最高价值的一条）

leader 的核心资产是"目标七问 + 第零问"。对照 lynn 现有简报四段（`member-runner.ts:44-77` 的 `validateBrief`）：

| 七问 | 落到 lynn 哪里 | 现状 |
|---|---|---|
| 0. 这张海图是你自己测的还是听来的 | 简报【前提核验】：动手前先验证材料/命令/路径真实存在 | **缺** |
| 1. 目的 | 简报【目标】 | 有 |
| 2. 完成态 | 简报【完成标准】 | 有 |
| 3. 证据（谁清点货舱） | 简报【验收口径】：每条验收贴实际输出，不是自述 | **缺**（现有 `read_artifact` 是验收**后**的闸，不是派单时的口径） |
| 4. 反作弊（不许劫商船凑数） | 简报【禁区】：点名禁止具体姿势（不许 skip 测试、不许 mock 被测对象…） | **缺** |
| 5. 地界（只许走这三条航线） | `assign_task.readRoots` / `workspace` + 简报【限制】 | 有雏形（工作区纪律 + 只读申请制） |
| 6. 取舍（保货还是保船） | 简报【优先级口径】：算得对 > 做得全 > 做得快 | **缺** |
| 7. 未知（别硬闯，记下来绕过去） | 成员回报里的"待裁决清单"，先跳过继续做别的 | 部分（`ask_user` + pendingPlan），但无"记录后跳过" |

→ 建议：简报从四段扩到**六段**（目标 / 完成标准 / 验收口径 / 材料与位置 / 地界与禁区 / 优先级与取舍），其中**【验收口径】与【禁区】是新增的必填项**；【前提核验】作为成员第一步的固定动作（对应 leader 的"任务 0"）。

### 11.3 防五种死法 → 风铃的对应与真缺口

| leader 的死法 | lynn 现状 | 处置 |
|---|---|---|
| 作弊达标（skip 断言/mock 被测/删测试/放松阈值） | 无机制 | 简报【禁区】点名禁止 + 判卷标准**派单时冻结**（写进契约卡），验收时按冻结口径 |
| 幻觉命令（编造命令再甩锅环境） | 风铃不能执行 → **无法亲手验证成员命令**，成员也会编 | 简报里风铃给的命令一律标"未验证"；成员第一步做前提核验，查不到就如实报"缺上下文"（member-runner 已有该语义，缺的是"先核验再动手"的强制顺序） |
| 失忆（进度写 PROGRESS.md） | 成员独立会话，无进度文件 | 可选：成员工作区写 `PROGRESS.md`，长任务（maxTurns>12）启用 |
| 一条道走到黑（同一验收连败 3 次换项） | `rejectLimit` 3 轮 ✓ | 已有 |
| 静默事故（坏了不发信号）+ 反向验证 | 无 | 简报【验收口径】加一条"反向验证：亲手制造一次失败证明会响" |

**"法与情报分家"**也值得抄：简报里"不许"是法（违规即不合格，每条溯源到一次实测或用户裁决），"建议"是情报（成员有更好的路可以走，但要记一句为什么）。现在 lynn 简报的"限制"段不区分二者，成员遇到分歧时不知道哪些能自己拍板。

### 11.4 暗卷 / 明卷 → lynn 的正确落法

leader 有"明卷（书里验收命令）+ 暗卷（2-3 条执行者看不见的抽查，自留不进书）"。lynn 里暗卷意义不大（执行者做完才验收），**真正对应的是"判卷标准派单时冻结"**：现在风铃可以在成员交回来之后临时改口径（"这个不算，重出"），成员永远无法证明自己按当时的标准做对了。

→ 落点：`PendingPlan` 契约卡（用户点"开始"才落权的那张）增加一节【验收口径】，成员可见；风铃验收必须按冻结口径判，打回要写清"当时的口径 vs 现在差在哪"。这与现有的 `read_artifact` 硬闸（2026-11-12 刚加）互补：那个闸防"没读正文就点头"，这个防"点头时换标准"。

### 11.5 多 agent 并行 → 正好是群聊模式的"群分工卡"

leader 的一条硬洞察：**"接缝没人接是头号事故"**。多 agent 并行必须每份书带同一段"全局"（整体干什么、谁管哪段、接缝在哪），地界错开、共享写入点指定唯一归属，"A 的证据经过 B 的战场只列存疑不动"。

lynn 的并行派单（一个群多张单）正缺这个：每张单的简报是独立的，接缝无人认领。而且"接缝"在群聊里有天然的呈现位置 —— **群里一条分工卡**：谁管哪段、接缝在哪、共享写入点归谁。

→ 建议 P1 加一条内核产物：`group.brief` / 群公告卡（整体目标 + 分工 + 接缝归属 + 判卷口径摘要），由风铃在派完单后自动落一张群卡。

### 11.6 其他可直接抄的小机制

| leader 机制 | lynn 落点 |
|---|---|
| 调研优先、只问查不到且会改变范围的（一轮 ≤5 问，每问给 2-4 选项 + 推荐） | 风铃的 `ask_user` 已是这个形态；`validateBrief` 的退回理由可照此"给选项" |
| ≤4000 字符硬上限，压不进就是活太大 → 拆 | 简报长度上限 + "活太大就拆单"判据（现无） |
| 执行型 vs 探索型分流（探索型硬指标只会收到凑数的答案） | **现无** → `assign_task` 增 `mode: "execute" | "explore"`，探索型不强压"证据条数"，改问"结论 + 依据 + 不确定性" |
| 交付三样、无过程噪音 | `report_to_user` 四段已接近；补"过程噪音不带" |
| 执行者不能自己批卷 | 已有：`accept_or_reject` 归风铃，成员不能自批 ✓ |
