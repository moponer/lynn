## 我们的差异

**1. 没有 git range 可用。** 上游按 commit 区间评审（`git diff base..head`）。我们的成员在任务工作区里干活，
评审对象是**产物本身**：用 `read_file` 读正文、`list_dir` 看目录、`run_command` 跑测试拿退出码。
不要假设仓库有干净的提交历史——多数单没有。

**2. 只评审本次派的活。** 上游会说「顺带看看邻近代码」。我们不顺带：范围就是派单简报里的【完成标准】，
越界评审会把别人的在办改动判成缺陷，制造假返工。

**3. 结论要能给风铃直接用。** 她是拿你的结论决定 `accept_or_reject`，不是拿你的过程。所以每条缺陷必须自带：
**位置**（文件:行 或 章节）、**为什么算缺陷**（违反哪条验收标准）、**怎么改**。

## 输出格式（我们的卡片口径）

```
【验收结论】<通过 | 不通过>
- 判据 1：<照抄完成标准原文> → 通过 / 不通过（证据：file:line / 命令输出）
- 判据 2：…
【必须改】（不通过才写，按严重度排序）
1. file:line —— 违反「判据 2」；改成 …（一句话能照做）
【存疑】<不确定但值得他看一眼的；没有就写「无」>
```

- 判据逐条对，**不合并、不概括**——风铃要拿未过项填 `failedChecks`，少一条就少返工一条。
- 「文件存在」不是通过；骨架稿、占位符（`undefined` / 空章节）只有读正文才发现。
- 明确写「无发现」比含糊其辞有用；有残留风险就单列一行。

## 自检

- [ ] 每条缺陷都能定位到具体位置吗
- [ ] 「不通过」的每一项都对应一条简报里的验收标准吗（不是我的个人偏好）
- [ ] 我有没有替风铃做决定（决定权在她，我只给结论和理由）
